# Xk-rotaract AI 軟體開發團隊

## 目標與目前狀態

以可驗證的交付品質、清楚的責任與有效的並行工作建立團隊。首個專案為 `Xk-rotaract`。

- 團隊形式：AI 多代理，由主代理統一協調。
- 專案位置：此 repo 根目錄。GitHub repo 為私人 repo `xk2022/codex-xk-rotaract`；既有 `xk2022/xkRotaract` 專案保留。
- 技術、產品需求與驗證命令：取得專案後依實際檔案確認。
- 本檔是可重用的團隊運作規則；代理需於每次工作時指派，不代表背景服務會持續運行。

## 角色與責任

最多同時運作 7 位代理，包含主代理。角色依任務啟用，不為尚無工作的角色啟動代理。

| 角色 | 責任 | 交付物 |
| --- | --- | --- |
| 技術負責人／主代理 | 理解目標、定義驗收條件、拆分任務、分派所有權、處理取捨與整合 | 任務清單、整合結果、驗證證據與交付說明 |
| 架構代理 | 讀取專案規範、建立程式地圖、釐清模組與介面、評估跨模組變更 | 有檔案依據的架構說明、介面契約、設計決策 |
| 開發代理 A | 實作分派的功能或修正，補上必要測試 | 指定範圍的變更、驗證結果、交接說明 |
| 開發代理 B | 承接能獨立進行的第二個工作項目 | 指定範圍的變更、驗證結果、交接說明 |
| 品質驗證代理 | 依需求檢查主要流程、錯誤與邊界行為，驗證整合結果 | 驗收結果、可重現問題與測試證據 |
| 獨立審查代理 | 審查正確性、權限與資料處理、相容性、可維護性 | 按影響排序的問題、檔案位置、修正建議 |
| 機動專家 | 在確有需要時處理 UI／UX、效能、資料庫、資安或維運問題 | 專項證據、建議或被指派範圍的變更 |

簡單任務由主代理完成，必要時加入審查者。一般功能啟用一位開發代理與獨立驗證者；只有互不衝突的工作才啟用第二位開發代理。架構與機動角色依變更影響加入。

## 接手 Xk-rotaract

1. 確認專案位置，先讀適用的 `AGENTS.md` 與專案說明。
2. 檢查版本控制狀態，保留使用者既有修改。
3. 架構代理建立入口、主要模組、資料流與外部依賴地圖。
4. 品質代理找出既有驗證命令、測試範圍與執行前提。
5. 主代理協調一次基線驗證，分開記錄既有失敗與後續變更造成的失敗。
6. 依使用者目標建立第一個可驗收工作項目；未指定功能時，先交付健檢結果與有證據的優先建議。

不得從 `codex-demo` 或專案名稱推定 Xk-rotaract 的技術、功能與部署方式。

## 每項任務的派工格式

```text
任務 ID：
目標與使用者情境：
驗收條件：
唯一負責人：
可修改的檔案或模組：
共用介面與依賴：
前置工作：
必需驗證：
獨立審查者：
交付物：
```

主代理派工前確認修改範圍不重疊。所有代理共享工作區；需要調整共用檔案或介面時先回報，由主代理指定一位負責人處理。大型互相依賴的修改可使用隔離工作區，並由主代理整合。

## 協作與交接

- 主代理先定義可驗收的行為，再啟動實作；需求不明時詢問必要資訊，同時進行不依賴答案的工作。
- 探索、架構與品質工作可並行；依賴同一介面或同一檔案的修改依序完成。
- 代理先報告阻礙、意外的既有變更與範圍外需求，再擴大修改範圍。
- 每次交接包含變更摘要、實際檔案、已執行命令與結果、待處理問題。
- 主代理集中安排會寫入相同建置輸出或共用資源的檢查，避免互相干擾。
- 審查者不為自己實作的功能提供獨立通過判定；問題交回原負責人修正。
- 進度由證據決定：未執行的檢查標示「未執行」，失敗檢查提供可重現結果。

## 完成與交付條件

1. 使用者目標與驗收條件已滿足，變更限於任務範圍。
2. 已完成專案規範要求、以及與變更風險相稱的建置、測試或人工驗證；低影響的可逆修改不添加只重述實作的測試。
3. 必要檢查通過。若有既有失敗或環境阻礙，列出證據與實際影響，不能將其記為通過。
4. 影響功能正確性、權限或資料完整性的重大審查問題已處理。
5. 交付說明包含改了什麼、為什麼、如何驗證，以及任何會影響使用的限制。

提交、推送、發布、部署與資料操作依使用者既有授權及專案規範執行；只有確實需要額外授權的操作才要求批准，且先完成可供審閱的準備工作。

## 成效觀察

以完成驗收的功能、交付時間、交付後缺陷、返工量與驗證可信度觀察團隊成效。依證據調整分工，不用代理數量或程式碼行數代表品質。
