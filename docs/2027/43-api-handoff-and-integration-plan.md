## 建議實作順序

沿用已確認的「會員／社團／權限優先，其次活動行事曆」。每一階段包含讀取、變更、錯誤處理與真實 API 瀏覽器驗收。

| 順序 | 實作範圍 | 主要依賴 | 完成判定 |
| --- | --- | --- | --- |
| 0：交接與測試環境 | 確認共同使用的程式版本、API 契約、合成帳號與資料庫；保留現有核心 live 回歸 | 後端交付與各 README | 前端開發者能讀取同一份契約與執行既有 live 流程；測試資料與正式資料分離 |
| 1A：會員、社團、權限 | 本人身分、有效管理範圍、會員多筆社籍、社團資料、角色任期、年度名冊 | Session、`/me`、`/members`、`/clubs`、`/role-grants` | 本社與本地區可操作範圍正確；隱藏聯絡資料不回填；撤權與停社立即反映 |
| 1B：社籍異動與歷史同意 | 入社、三段轉社、退社／OB、歷史顯示、本人同意、稽核、必要 MFA | 1A 的資源 ID、版本與範圍 | 雙社核准後仍由本人執行；失效須重審；本人未同意保持隱藏；管理者權限符合矩陣 |

## 串接前已確認的模型差異

| 現有示範模型／行為 | API 契約與接手方式 |
| --- | --- |
| `domain.ts` 的會員只有單一 `clubId` | 讀取 `clubs` 與社籍投影，保留每筆社籍 ID、類型與歷史；支援同時一扶青社籍加一扶輪社籍，不能以單一欄位覆蓋 |
| 示範資料使用 `taipei`、`m1` 等 ID | API 使用永久 UUID；畫面選項及深連結須使用查詢得到的 ID，不以名稱或帳號代號代替 |
| 年度狀態以簡化 `confirmed/unconfirmed` 表達 | API 另有 `grace`；7 月寬限須獨立顯示，不能當作明確未確認；日期依 Asia/Taipei |
| 示範轉社狀態為 `ready`，核准以 boolean 表達 | API 為 `ready_for_member`、`needs_reapproval` 及核准資料；保留重審狀態、到期時間與回覆版本，最終使用 execute 操作 |
| 歷史以陣列 index 及 `visible` 操作 | 使用 membership UUID、`contentVersion`／`visibilityVersion` 與公開請求 UUID；本人同意必須綁定該筆內容，畫面不以 index 當資源 ID |
| 支援示範把補件叫 `supplement`，核准後由畫面切換後續階段 | API 明確回 `awaiting_evidence`、`awaiting_new_email_proof`、`awaiting_password_reset` 等；核身核准、信箱確認及實際重設分別呈現 |
| 示範角色切換與商家會員下拉選單決定身分 | API 以登入 Session 與目前授權為準；前端只選擇已授權範圍，`GET /me/tasks?scope=business` 仍使用登入者自己的會員身分 |
| 共同維護邀請建立時使用 `inviteeId`；撤權使用 companyId/memberId | 建立請求為 `memberId`、`kind: editor` 及公司 `version`；撤權先取得對應已接受邀請的 UUID 及邀請版本，再呼叫 `/company-invitations/{id}/revoke` |
| 邀請示範可能從 version 1 開始，且部分操作不變更公司版本 | API 的初始版本與遞增以回覆為準；決定邀請時 `version` 是邀請版本、`companyVersion` 是公司版本，成功後更新兩者或重新讀取 |
| 商家回報的示範 `assignedTo` 使用操作者 memberId | API 的 `reporterId` 是會員 UUID，`assignedTo` 是承辦帳號 UUID；不要以兩者相等判斷權限 |
| `TaskItem.view` 的示範 union 沒有 `history` | API 待辦包含歷史公開同意入口；串接時擴充畫面型別並導向既有歷史頁 |
| 前端可從全部合成商家計算曝光、確認數及本人紀錄 | 正式讀取伺服器投影與資格結果；本人確認紀錄由 `/me/business-confirmations` 取得，公司隱藏仍可撤回，畫面不需要取得其他人的確認資料 |
| 圖片示範使用 URL 或檔案預覽 | 上傳後使用資產 UUID；頭像、公開社徽與私有證據的讀取權限不同，私有圖片不得轉存公開 URL |

欄位映射屬於前端資料轉換層；請求仍遵守 OpenAPI 的欄位白名單。姓名、電話或 Email 不作為永久關聯鍵。

新增前端差異：ICS／分享可使用既有公開活動投影；收藏持久化 API 仍待補齊，年度交接總覽需對齊伺服器年度及任期規則。這些是前端基準之後的新增工作，尚未包含在本輪 141 項 API 的串接驗收中。

## 第一個串接工作項目：會員、社團與有效權限

這是下一個建議實作單位，尚未執行。

- [ ] 沿用現有登入 client，讀取 `/me` 的會員、有效 roles、availableScopes 與 mfaAuthenticated；角色到期、停社或撤權後重新整理可操作範圍。
- [ ] 會員列表／詳情使用 API 投影，隱藏聯絡欄位省略時顯示適當文字；伺服器版本獨立保存，不與示範資料合併。
- [ ] 社籍畫面保留目前及歷史多筆關聯、社團類型與各筆 UUID；年度確認使用對應 membership 版本。
- [ ] 社團維護與角色清單依有效範圍載入，社長／秘書／一般管理者／備援／地區角色分別驗收。
- [ ] 更新遇 409 時保留使用者草稿、重讀最新內容並讓使用者確認；不得自動覆寫或自動重新送出核准。
- [ ] 以兩個不同社團的實際登入帳號驗收跨社拒絕、即時撤權及隱私投影。

共通錯誤要區分：400 欄位驗證、401 登入或本人驗證失敗、403 特定動作或 MFA 要求、404 不存在／不可見、409 版本或狀態衝突、429 限流及 503 暫時不可用。本人密碼錯誤的 401 先重新查 `/me`，確認 Session 狀態後再決定是否導向登入。

## 每個階段的驗收方式

1. 對照 OpenAPI 確認必要 query、請求欄位、回覆投影及資源版本；分頁預設 20，pageSize 範圍 20～100。每種列表是否分頁以個別 DTO 為準。
2. 使用 HTTPS 前端及同源 `/api` 代理，Cookie 由瀏覽器管理；變更請求帶 CSRF 與契約要求的 Idempotency-Key。同內容重試沿用 key，新的操作使用新 key。
3. 成功後使用伺服器回覆或重讀結果更新畫面，並驗證重新整理仍保留資料；失敗時保留草稿，避免出現假成功。
4. 在 `frontend/` 執行 `npm test`、`npm run build` 及該功能新增的真實 API 瀏覽器流程；既有 `test:browser:live`／`test:browser:live:account` 保留為核心回歸。
5. 當後端或契約有變更，執行 `python3 docs/api/build_contract.py --check`、`python3 docs/api/validate_contract.py` 及依 backend README 配置的 `mvn verify`。測試重設只可用明確允許的獨立 `_test` 資料庫。

目前 `test:browser:phase2`、商家、優惠及 engagement 等腳本主要驗證示範資料流程；各階段需另補使用真實 API 的瀏覽器驗收，不能直接將既有示範測試記為串接通過。
