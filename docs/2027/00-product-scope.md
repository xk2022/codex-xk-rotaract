# 產品範圍與設計原則

> 現行狀態（2026-10-15）：剩餘規格已依使用者授權補齊，請先讀[需求基準 v1.0](13-requirements-baseline.md)、[權限矩陣](14-role-matrix.md)及[現行階段清單](11-development-phases.md)。下方保留來源分析與歷次討論；其中「待確認／提案」及舊狀態僅供追溯，已由現行基準處理。程式與驗收尚未完成。

## 來源與歷次討論（非現行待辦）

## 舊版與新版定位

舊版同時提供公開網站、社團與會員資料管理、活動行事曆及公司地圖，另有 UPMS 管理工具。新版建議定位為「扶青社資料與活動管理平台」，職業交流為後續模組；這是供討論的定位，不是已核定產品策略。

新版 repo 目前只有 `frontend/`、`backend/` 及文件骨架，尚無技術選型。舊版 Java／Thymeleaf／MySQL 為參考來源，不直接指定為新版技術。

## 候選角色

| 角色 | 建議責任 | 資料範圍 |
| --- | --- | --- |
| 訪客 | 閱讀核準公開的社團、活動與公司資訊 | 僅公開欄位 |
| 會員 | 維護自己的資料、瀏覽獲準內容 | 自己及獲準公開資訊 |
| 社團管理者 | 維護社團、社內會員與活動 | 被授權的社團 |
| 地區管理者 | 維護地區與轄內資料 | 被授權的地區 |
| 平台管理者 | 帳號授權、分類與平台設定 | 明確授權的管理操作 |
| 企業申請／繳費紀錄管理者（候選） | 登錄與作廢企業申請／繳費紀錄 | 被授權的公司或組織 |

角色名稱、是否兼任與跨組織授權均待確認。平台管理權不代表可任意公開個資。

## 範圍邊界

保留候選：登入、權限、地區社團、會員、自助修改、活動行事曆、公司名錄、公司地圖、人工企業申請／繳費紀錄與公開社團展示。

建議調整：明確公開／私有欄位、資料範圍授權、活動發布狀態、日期時區規則、結構化關聯、稽核與資料品質。

未納入預設 MVP：活動報名、簽到、線上付款、發票、即時聊天室、社群登入、LINE 通知、手機原生 App、自動會籍年度轉換。若要加入，另開需求與驗收，不由舊版頁面名稱推定。

UPMS 的系統、選單、字典、日誌等模組需逐一確認保留必要性；不預設複製整套通用管理平台。Demo 與模板示例不列為產品功能。

## 端到端成功情境（建議）

社團管理者登入 → 維護被授權的社團 → 建立活動草稿 → 發布 → 訪客在指定地區與月份看到活動 → 管理者取消活動 → 公開端明確標示取消。其他社團管理者不能修改此活動。

先以此流程討論畫面、資料、API 與驗收，再選技術。第一階段不以功能頁數代替可驗收流程。

## 已確認的優先方向（2026-10-14）

先會員／社團資料與權限，再活動行事曆。需要沿用舊系統資料，先盤點與清理後分批移轉。此決策確認方向，不代表核定全部候選功能、角色、技術或授權開始程式開發。

## 已確認的管理範圍（2026-10-14）

社團管理者只能管理自己社團；地區管理者可管理轄內社團。此確認不涵蓋平台管理者權限、角色授予、會員個資公開或跨區移轉；具體動作與欄位仍待定稿。

## 已確認的社籍方向（2026-10-14）

會員同一時間最多一個扶青社籍，可同時有一個扶輪社籍；採社籍子表關聯與社團類型，預留青商會與 BNI，保留歷史社籍供經歷顯示或備查。詳見 [社籍規格](12-membership-and-history.md)。未來體系的上線階段與管理階層仍待確認。

## 已確認的歷史公開決定權（2026-10-14）

歷史經歷由會員自行決定是否公開；較高權限管理者可協助隱藏，非 admin 重新公開須透過彈窗取得會員本人明確同意；admin 可例外直接公開。例外僅適用此公開操作，詳細設計見 [歷史公開機制](12-membership-and-history.md)。
