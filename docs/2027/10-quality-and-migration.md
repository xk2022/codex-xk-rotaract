## 舊資料移轉前提

目前只取得舊程式碼，未取得資料庫 schema 匯出、資料量、正式版本與資料保留政策；不能宣稱舊資料可直接轉入。使用者已確認需要沿用舊資料，先盤點與清理後分批移轉；來源取得、清理規則、批次範圍與切換方式仍待確認。本次僅規劃，不讀取或移轉正式資料。

1. 取得授權後由安全管道提供結構及去識別化樣本；不得提交正式個資或憑證。
2. 盤點 schema、資料筆數、狀態、字典分類、孤兒關聯與重複資料。
3. 建立舊 UPMS 組織 ID、CMS 地區／社團 ID、会员字串 ID 之间的映射，不能用數字相同判定同一組織。
4. 驗證 `CmsClubInfo` key-value、公司產業逗號字串、座標字串與日期時间；不合格資料進隔離報告，不靜默丟棄或猜值。
5. 企業 Pay 記錄需先確認「申請／繳費」語意；不可從單一日期推算金額、付款成功或訂閱效期。
6. 密碼處理與舊凭證不可照搬；設計受控帳號啟用／重設流程並驗證持有權。
7. 建立可重複的試轉：數量、關聯、公開欄位、日期邊界與文件附件核對；由業務擁有人確認差異。
8. 再決定凍結／增量、切換、回復、保留與刪除步驟。切換先做還原演練，不能只靠匯入成功。

## 基線與責任

舊版已觀察的安全風險見 [舊版風險](../2024/risks-and-migration.md)。此任務不對正式站進行漏洞測試，也不修改舊版程式。新版安全與權限規格應在第一條主流程之前完成；實作與獨立驗收分開。

## 社籍移轉與清理

依 [社籍規格](12-membership-and-history.md) 將舊社籍建立為子表資料，不以單一會員主表 clubId 覆蓋歷史。先驗證舊社團 ID、類型與同一人識別，再確認有效社籍與歷史期間。

- 舊 `rotaract_id` 與組織／社團 ID 先映射核實；其他來源類型不從名稱猜測。
- 同類型多筆有效社籍、重複會員、孤兒關聯與期間重疊進清理清單，由業務擁有人確認；不自動保留最後一筆。
- 未知起迄日期、轉社時間或會籍狀態如實標示來源與待核實情況；不得用匯入日期冒充入社日期。
- 分批驗收有效扶青社與扶輪社籍各至多一筆、歷史筆數、類型一致性及經歷可見範圍。沒有來源證據的歷史不捏造，缺漏列入盤點報告。

## 歷史公開驗收與移轉

逐筆驗證本人公開決定權、非 admin 管理者隱藏與請求同意、本人端彈窗、未回覆／拒絕不公開，以及 admin 例外的身分驗證與稽核。公共入口撤回、請求失效、同意重放和競爭更新納入驗收，詳見 HIST-VIS-AC 系列。

移轉時不把舊公開狀態或一般管理者操作視為會員的新同意；預設隱藏為提案。正式採用預設值前需確認，且移轉報告須列出歷史公開設定與已知同意證據。此次不建立同意請求、不通知真人或操作正式資料。
